# Questions — Local research runtime

Living record. Open questions first, then the decisions already taken so they are not re-proposed.

## Open

Four questions remain of the seven opened by the review of 2026-09-12, after every document in this folder had been signed off and before phase 01 started; R-18, R-19 and R-20 were answered on 2026-09-12 and have moved to the table below. Each one fixes a shape the phases build on rather than a detail inside a phase, so each one is answered before implementation begins; the documents carry an **Open** marker wherever one of them decides their wording. The evidence column names the shipped code that makes the question real.

| # | Question | Why it blocks | Options on the table | Evidence |
| --- | --- | --- | --- | --- |
| R-17 | Which id is a local research keyed by? `research/<task_id>/`, the worktree, the lock and `research cancel <task_id>` all name one, but under `mode: local` no worc task exists when the research starts. | It is the key of every file the runtime writes and of the operator's own cancel command, and it decides which id the item's "Queued as worc task" comment names. [AC-R9](acceptance-criteria.md) cannot be written until it is fixed. | **(a)** the research reserves `seq` 1 exactly as the worc path does — a row with `stage: research` and no worc task behind it — and the implementation task is `gh-142.2`, so ids read the same in both modes; **(b)** the research runs under the id of the implementation task it will produce (`gh-142`) and reserves nothing, so a local item costs one id where a worc one costs two. | `core/reconcile.py` `_implement` allocates `seq + 1`; `docs/configuration.md` documents "`gh-142` triaged → `gh-142.2` implemented". |
| R-21 | Who renders `RESEARCH_TASK.md`, and from what? | The child is launched with a `task_id` and nothing else, and `run.json` records the item's id and update stamp, not its text. Either the parent renders the file at `start()` and the child copies it into each fresh worktree, or the child reads the item from the tracker again — which puts an adapter inside `research/` and breaks [D14](design.md), because the text the child would fetch is not the text the research started on. | **(a)** the parent renders at `start()` into the run directory and the child copies it per attempt — the shape the data section already implies; **(b)** the child fetches the item itself. | The design's own diagram puts the write inside the child; the data shapes put the file in the run directory. |
| R-22 | What environment does the agent process get? | [D12](design.md) says "no forwarded secrets"; D4 and phase 03 say "the connector's own environment". They are the same environment, and on the operator's machine it carries `GH_TOKEN`, `ANTHROPIC_API_KEY`, `SSH_AUTH_SOCK` and whatever else the shell that started `watch` held. The agent is unsandboxed and runs on text written by strangers, so this is the one place the two sentences cannot both stand. | **(a)** an allow-list — `PATH`, `HOME` / `USERPROFILE`, the locale, and the variables the agent CLI needs for its own login; **(b)** the connector's environment minus a deny-list of known credential names; **(c)** the full environment, and D12 drops the claim rather than making it twice. | `trackers/github/gh.py` forwards the environment deliberately, because that _is_ how `gh` authenticates — an agent is not that case. |
| R-23 | Does `gate.allow_all: true` stay allowed together with `research.mode: local`? | D12 makes the gate the security perimeter of this whole feature, and `allow_all` is the one supported configuration that removes it: every open item of the repository would start an unsandboxed agent with the operator's permissions on a stranger's text. | **(a)** the loader refuses the combination and names it; **(b)** `doctor` and `watch` print a warning naming the exposure and start anyway; **(c)** nothing — an operator who wrote `allow_all` wrote it with their eyes open. | `config.py` `_gate` already treats "no rule" as invalid; this is the same reasoning one step further. |

## Decided

| # | Question | Decision | Date |
| --- | --- | --- | --- |
| R-19 | Does the worc-side path move behind `ResearchProvider`, or is the seam the local producer alone? | **Symmetry in the configuration, not in the code (a).** One key still selects three complete modes, but the `worc` producer is not moved behind a protocol it does not fit: `ResearchProvider` describes the local producer, the composition root branches on `research.mode`, and `core/reconcile.py` keeps the worc path exactly as phase 07 shipped it — `worc:queued` and `worc:in-progress` while the triage task runs, and no `cancel`, because a task handed to worc is worc's. The symmetry that matters is downstream of the report, where one reader, one builder and one write-back already cannot tell the two apart. Rejected: widening the protocol until both fit (two shapes wearing one name); refactoring `reconcile.py` around it (rewriting a landed path for a symmetry nobody reads). | 2026-09-12 (user) |
| R-20 | Where do the research clone and its worktrees live? | **A `research.workspace` root outside worc's clone (a), holding `repo.git` and `worktrees/` — and the run directories stay where they are.** Decided against worc's own source rather than against a rule: worc creates no worktrees (its only worktree code is defensive, for the case of being run inside one, and it denies its own agents write access to `git_dir` and `git_common_dir`), and it never runs `git clean` (every `clean` in its source is the `worc logs clean` / `worc runs clean` subcommand), which withdraws the "a `git clean -xfd` would delete a running research" argument entirely — so `research/<task_id>/` stays in `.worc-connect/` and the home is not split for that reason. What survives is two things a shared clone cannot avoid: the agent would share worc's refs, objects and hooks (`git branch -D worc/gh-140`, `git gc`, and a repo-wide `core.hooksPath` that makes the agent's first commit run worc's hooks), all of which worc fingerprints in `GitControlState` before and after every provider attempt and reports as drift a human is asked about; and an agent CLI started inside the clone reads `CLAUDE.md` / `.claude/` from its **ancestor** directories, so a research pinned to `origin/HEAD` would be steered by instructions out of worc's live, mid-task working tree. Rejected: keeping it under `.worc-connect/` (b). Stated plainly in D3: this removes the accident, not the intent — the agent holds the operator's permissions and can walk anywhere on purpose. | 2026-09-12 (user) |
| R-18 | How is a row in `researching` revisited once the tracker stops listing its item? | **A pass over the live rows of the store (a)**, resolving with `adapter.get_item` only the rows the listing did not already return. The costs were measured rather than guessed: `list_items` is one `gh` call whatever the window, `current_state` makes none at all (it reads the labels off the item already fetched), and `get_item` is one call per row — so a tick with no research in flight costs **exactly nothing** extra, and a tick with research costs at most `max_concurrent` calls. Rejected: holding the watermark back (still one call, but the page grows with the length of the longest research, and `gh issue list --limit 200` truncates the _newer_ end, so one long research would starve every new item); a mandatory timeout, which would have reversed R-6. | 2026-09-12 (user) |
| R-1 | Where does the research agent run — a worc task (phase 07), a worc-side queue lane, a second worc instance, or a runtime inside the connector? | **A runtime inside the connector.** The alternatives were laid out with their costs; the operator chose the local runtime for throughput and for keeping it to one process tree, explicitly without a sandbox. | 2026-09-11 (user) |
| R-2 | Does the local provider replace the worc-side triage of phase 07? | **No — they coexist** behind one `ResearchProvider` seam, chosen by `research.mode`. Phase 07 stays the default and the fallback for a host with no agent CLI. | 2026-09-11 (user) |
| R-3 | Does the item get a state of its own while research runs? | **Yes**, `worc:researching` (D9). | 2026-09-11 (user) |
| R-4 | Is the report format shared with phase 07? | **Yes, one-to-one** — same verdict block, same reader, same builder; only the producer differs (D5, FR-R10). | 2026-09-11 (user) |
| R-5 | Are preconditions checked up front? | **Yes** — a `doctor` command, and `watch` refuses to start with `research.mode: local` when a check fails (D11). | 2026-09-11 (user) |
| R-6 | Is there a timeout? | **Opt-in only.** `timeout_seconds: 0` or the key absent means no timeout at all; the bound is the operator's (`status` + `research cancel`) and `max_concurrent` (D8). | 2026-09-11 (user) |
| R-7 | One agent or several? | **Several, ordered, with fallback** — Claude Code and Codex ship as named profiles; the next agent runs only when the previous **fails**, never because of a verdict (D7). | 2026-09-11 (user) |
| R-16 | What happens to a research's working files (`agent.log`, `RESEARCH_TASK.md`, `run.json`) once it ends? | **The operator configures it:** `research.retain` — `on_failure` (default: a successful research keeps `report.md` and `outcome.json`, a failed or cancelled one keeps everything), `always` (nothing is deleted), `never` (only `outcome.json` survives). `research.retain_max_runs` prunes the oldest retained run directories beyond N (0 = no cap), applied at startup and after each dispatch, so the home cannot grow without bound under any setting (D16). | 2026-09-11 (user) |
| R-15 | Where do the `claude` / `codex` argv come from? | **Pinned constants, overridable.** Two shipped profiles are fixed in code — including each CLI's non-interactive / auto-approval flag, whose exact spelling is verified against the installed CLIs when phase 05 is implemented, not guessed now — and `doctor` prints the resolved launcher, its version and the **full argv** it would run, so what is being granted is visible rather than implied. Any other CLI, or a moved flag, is the table form in the configuration. Rejected: parsing `--help` to build argv (a heuristic over someone else's prose that fails silently); shipping no defaults (every operator re-derives the same two lines). | 2026-09-11 (user) |
| R-14 | With no timeout by default, what bounds a run? | **The operator, through a first-class kill command.** `worc-connect research cancel` takes a `task_id`, an item, or `--all`, and ends the research **and the agent process it started** — including an agent orphaned by a dead child, which is why the agent's own PID is recorded next to the child's. `status` lists every running research with agent, item, elapsed time and both PIDs. `max_concurrent` still caps how many can be in flight. No timer is armed unless `timeout_seconds` is set (R-6). The kill path is explicitly cross-platform: process groups and terminate-then-kill, no signals, exercised on both platform branches (D15). | 2026-09-11 (user) |
| R-13 | An item is edited or re-triggered while its research runs. | **Let it finish, and say so.** The research completes on the text it started with; the run records the item's `updated_at` at start, and when it advanced by dispatch time the task body and the comment carry one line saying the item was edited after the research began (D14). Re-trigger rules are unchanged: an edit alone triggers nothing, a re-applied label or a reopen allocates `seq + 1` and a fresh cycle. Rejected: cancelling and restarting on the new text (a series of edits starves the item and burns tokens); finishing silently (the operator cannot tell the report is stale). | 2026-09-11 (user) |
| R-12 | Does report text reach the issue as a comment? | **One field, every verdict:** the report's `reason` paragraph is quoted inside the connector's own comment template, length-capped and neutralised (`@mention` and `#123` defused so an agent cannot ping people or cross-link issues), and nothing else from the report is published (D13). Rejected: the full report in a `<details>` block (unbounded model text, written from untrusted input, on a public tracker); publishing only on the no-task verdicts (the author of an `actionable` issue benefits most from knowing it was reproduced); publishing nothing (leaves a `declined` with no reason on the item). | 2026-09-11 (user) |
| R-11 | What is `base_ref` by default? | **The clone's own default branch** — `origin/HEAD`, which `git clone --bare` sets from the remote and `git remote set-head origin -a` refreshes on fetch. No API call, no adapter dependency in the research path, and `master` / `develop` need no configuration; the `base_ref` key overrides it. Rejected: `gh repo view --json defaultBranchRef` (a second network failure mode for a value git already has) and a hard-coded `origin/main` (silently wrong on any other default branch). | 2026-09-11 (user) |
| R-10 | How are the three ways of running the connector (no research / research through worc / native research) expressed? | **One key, three values:** `research.mode: off | worc | local`, default `off`, each value a complete and independent configuration (FR-R1, FR-R1a, D2). Replaces the `triage.enabled`+`triage.mode` pair in both records; phase 07 is not implemented yet, so it ships the new name. Rejected: two keys (one meaningless combination); a per-item label override (hands the label-setter a lever the tracker-connector record deliberately refused). | 2026-09-11 (user) |
| R-8 | Whose clone does the worktree come from? | **The connector's own bare clone**, never worc's — no race with worc's git, and the "no `git` in worc's clone" invariant survives (D3). | 2026-09-11 (proposal, to confirm) |
| R-9 | Is a sandbox / permission profile / diff gate part of this? | **No**, by the operator's explicit choice. The two zero-cost guards stay (disposable worktree, push URL disabled) and the residual risk is stated in D12 rather than mitigated. | 2026-09-11 (user) |

## Rejected alternatives (recorded so they are not re-proposed as new)

- **A worc-side triage lane** (`queue: triage` with parallel queues, or a second worc instance in a second worktree) — keeps the "no agent runtime" invariant and needs no new security posture, but costs a change in the orchestrator repository or a second daemon and clone for the operator to run. Weighed 2026-09-11, not chosen.
- **Deterministic, model-free pre-research inside the connector** (stack-trace to file candidates, `git log -S`, duplicate search) — cheap, safe and inside every current invariant, but it is not what the operator asked for here. Kept as a separate deferred item in [out-of-scope.md](out-of-scope.md).
- **Running the agent against worc's clone or a worktree of it** — races worc's own git operations and puts an unsandboxed agent inside the tree worc commits from (D3).
